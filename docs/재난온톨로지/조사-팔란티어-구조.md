## 1. 온톨로지 — 명사 층과 동사 층

- 정의는 "조직의 운영 계층". 데이터셋 · 모델 위에 얹어 현실 대상과 잇는다. **명사 층 = 객체 · 속성 · 링크, 동사 층 = 액션 · 함수 · 동적 보안.** [문서](https://www.palantir.com/docs/foundry/ontology/overview)
- 객체 유형 = 현실 개체 · 사건의 틀, 속성 = 그 특성, 링크 유형 = 두 객체 유형 사이 관계, 액션 유형 = "사용자가 한 번에 가하는 객체 · 속성 · 링크 변경 묶음" + 부수효과, 함수 = 코드 로직. 비유는 객체 유형 ≈ 테이블, 객체 ≈ 행, 속성 ≈ 열, 링크 ≈ 조인. [문서](https://www.palantir.com/docs/foundry/ontology/core-concepts)
- 인터페이스 = 여러 객체 유형이 공유하는 '모양'(예: 시설 ← 공항, 공장). 인터페이스 기준으로 만든 흐름은 새 유형이 생겨도 그대로 통한다. [문서](https://www.palantir.com/docs/foundry/interfaces/interface-overview)
- 원천과의 관계: 원천 데이터셋을 읽어 객체 DB 에 색인하고, 원천이 바뀌면 따라 갱신한다. **사용자 편집은 따로 적용한다.** [문서](https://www.palantir.com/docs/foundry/object-backend/overview)
- 편집과 원천이 부딪치면 객체 유형별로 '사용자 편집 우선(기본)' 또는 '가장 최근 시각 우선' 중 고른다. [검색요약](https://www.palantir.com/docs/foundry/object-edits/how-edits-applied)

## 2. 액션과 되쓰기

- 액션은 단일 트랜잭션이며 파라미터 · 규칙 · 부수효과(알림 등)를 가진다. [문서](https://www.palantir.com/docs/foundry/action-types/overview)
- **제출 조건**: 조건이 모두 맞아야 제출된다(현재 사용자, 파라미터 값, 실행 맥락). 조건마다 실패 안내문을 단다. [문서](https://www.palantir.com/docs/foundry/action-types/submission-criteria)
- 외부 반영: 되쓰기 웹훅은 객체 변경 **전에** 실행되고 실패하면 아무것도 바뀌지 않는다. 부수효과 웹훅은 변경 **후** 최선노력으로 실행된다. [문서](https://www.palantir.com/docs/foundry/action-types/webhooks)
- **액션 로그는 그 자체가 객체 유형이다.** 제출 1건 = 로그 객체 1개이고 편집된 모든 객체에 링크된다. 누가 · 언제 · 액션 버전 · 파라미터 · 되돌림 여부를 담는다. [문서](https://www.palantir.com/docs/foundry/action-types/action-log)

## 3. 계보 · 버전 · 권한

- 데이터셋은 Git 식 트랜잭션(스냅샷 / 덧붙임 / 갱신 / 삭제)으로 쌓이고, 과거 보기가 곧 과거 버전이다. [문서](https://www.palantir.com/docs/foundry/data-integration/datasets)
- 계보 도구는 상 · 하류 관계, 빌드 시각, 생성 코드를 보여 준다. [문서](https://www.palantir.com/docs/foundry/data-lineage/overview)
- 표시(marking)는 강제 통제, 역할은 재량 통제. 표시는 **데이터 의존관계를 따라 파생 데이터에 자동 상속**된다. [문서](https://www.palantir.com/docs/foundry/security/markings)
- 행 단위 제한 보기, 객체(행) + 속성(열) 보안 정책 = 셀 단위. [문서](https://www.palantir.com/docs/foundry/security/restricted-views)
- 민감 행위 앞에서 사유 입력을 요구하고 기록하는 Checkpoints. [검색요약](https://www.palantir.com/docs/foundry/checkpoints/overview)

## 4. AIP — LLM 이 온톨로지를 쓰는 방식

- LLM 에 주는 도구는 **객체 조회 / 액션 적용 / 함수 호출 / 계산기**. "LLM 은 도구 사용을 요청할 수만 있고 실행은 플랫폼이 한다" — 호출한 사용자의 권한 안에서. [문서](https://www.palantir.com/docs/foundry/logic/blocks)
- "모델은 사용자가 읽을 권한이 없는 데이터를 볼 수 없다." 단, 이 통제가 모델의 출력까지 미치지는 않는다고 문서가 명시한다. [문서](https://www.palantir.com/docs/foundry/logic/overview)
- **사람 승인**: 편집은 임시 저장소에 대기했다가 적용된다. 자동화와 묶으면 **제안(proposal)**으로 세워 두고 검토자가 근거를 본 뒤 수락해야 액션이 실행된다. [문서](https://www.palantir.com/docs/foundry/logic/staged-writes)
- 챗봇의 액션은 '자동 실행' 또는 '사용자 확인 뒤 실행' 중 설정한다. [문서](https://www.palantir.com/docs/foundry/agent-studio/tools)

## 5. 시나리오 · 경보

- **온톨로지 시나리오**: 실데이터를 건드리지 않는 격리된 갈래. 액션을 적용해 만들고, 여러 개를 비교하며, 본판 반영은 별도 권한으로 한다. [문서](https://www.palantir.com/docs/foundry/ontology/overview-ontology-scenario)
- **Automate**: 조건(시간, 신규 객체 · 임계 초과, 데이터 갱신) → 효과(액션 제출, 함수 실행, 알림). 중대한 변경은 사람 검토용으로 대기시키라고 권고한다. [문서](https://www.palantir.com/docs/foundry/automate/overview)

## 6. 재난 · 위기 사례

객체 · 연결이 구체적으로 공개된 것은 거의 없다.

- 허리케인 샌디(2012): Direct Relief 가 자체 DB · 협력 진료소 · 공공 데이터를 합쳤고, 현장에서 침수 구역 · 약품 재고 · 피해 수준을 스마트폰으로 보고했다. [2차](https://www.directrelief.org/2012/10/hurricane-sandy-using-technology-for-effective-response/)
- 코로나 백신(Tiberius): 관할별 주간 배분량 계산에 쓰였다. 현장 활용이 제한적이었다는 보도가 있다. [2차](https://www.pressreader.com/usa/usa-today-us-edition/20210304/281487869085953)

## 8. 이 프로그램에 옮긴다면 (SQLite 최소판)

| 구분 | 이름 | 최소 구현 | 본뜬 개념 |
|---|---|---|---|
| 객체 | 지구 | 기존 자료 + 유형 열. 유형별로 쪼개지 말고 공통 열만 맞춘다 | 객체 유형 · 인터페이스 |
| 객체 | 읍면동 · 대피소 · 담당자 · 관측소 · 특보 | 각 1 테이블, 고정 키 | 객체 유형 |
| 객체 | 기준(통제 · 대피) | 행 = 조건식 + 출처(위키 문서) | 속성이 아닌 객체로 — 연결 · 이력 가능 |
| 객체 | 관측값 | (대상, 시각, 종류, 값) 덧붙이기만. 격자는 지구별 집계값만 | 시계열 |
| 링크 | 지구–읍면동 · 지구–대피소 · 지구–담당자 · 지구–기준 · 지구–관측소 | 외래 키 또는 연결 테이블 | 링크 유형 |
| 행위 | 통제 · 대피 권고 · 해제 · 기준 수정 | 종류마다 함수 1개: 검증 → 한 트랜잭션에서 상태 변경 + 로그 삽입 | 액션 유형 · 제출 조건 |
| 로그 | 결정 | 행 = 누가 · 언제 · 행위 · 파라미터 · **근거 관측값 스냅샷**, 대상 객체와 연결 | 액션 로그를 객체로 |
| 편집 분리 | 원천 수집 vs 사람 편집 | 조회는 편집값 우선, 없으면 원천 | 사용자 편집 우선 병합 |
| 경보 | 감시 규칙 | 수집 직후 기준 × 관측값 평가 → **제안 행** 생성, 사람이 수락하면 행위 실행 | Automate + 제안 |
| AI | LLM 도구 | 조회 + '제안 작성'만. 행위 직접 실행 금지 | LLM 은 요청만 |
| 만약에 | 시나리오 | 시나리오 번호를 단 편집(강수 가정) → 같은 규칙 평가 | 온톨로지 시나리오 |

가장 값진 세 가지:
1. 결정은 반드시 행위 함수를 거쳐 로그 객체로 남긴다.
2. 원천과 사람 편집을 분리한다.
3. LLM · 자동 규칙은 '제안'까지만 하고 실행은 사람이 수락한다.
