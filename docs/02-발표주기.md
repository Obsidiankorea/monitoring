# 예측 분포 발표 주기 — 실측

`nph-qpf_ana_img`(융합 QPF)가 **언제 새 발표분을 내놓는지** 직접 재서
감시 구간과 호출량을 정한 근거. 추측한 값은 쓰지 않았다.

## 발표를 어떻게 알아내나

⚠️ **아직 안 나온 `tm`을 주면 API가 최신 발표분으로 조용히 바꿔 돌려준다.**
그래서 "요청이 성공했으니 나왔다"고 판단하면 안 된다.

처음에는 `tm=T`와 `tm=T-10분`의 이미지를 통째로 해시해 비교했다. **틀린 방법이다.**
무강수면 연속 발표분의 강수역이 완전히 같아 영원히 "미발표"로 읽힌다.
실제로 지연 0.0분이라는 말이 안 되는 값이 나왔다.

다음으로 이미지 왼쪽 아래의 발표시각 글자만 잘라 해시해 봤다. 강수역이 같아도
이 글자는 발표마다 달라지므로 앞의 문제는 풀린다. **그런데 이것도 버렸다.**
발표 스탬프가 그림보다 먼저 바뀌기 때문이다 — 19:30 발표는 스탬프가 19:31에
바뀌었지만 그림은 19:38에도 비어 있었다. 스탬프를 믿고 받으면 흰 그림을 저장한다.

**지금 쓰는 방법**: 스탬프를 보지 않는다. **그림이 실제로 있는지**로만 판정한다.
가진 것 다음 슬롯부터 앞으로 한 칸씩 훑다가, 빈 그림이 나오면 거기서 멈춘다.
그 직전이 '올라온 마지막 발표분'이다.

```
가진 것 다음 슬롯부터 ── 한 장(ef=첫 칸)만 받아 본다
  색이 두 가지 이하면 → 아직 안 올라왔다. 멈춘다.
  그림이 있으면       → 여기까지는 있다. 한 칸 더 간다.
멈춘 자리 직전 = 받을 발표분 (가장 최신 것만 받는다)
```

확인 비용은 슬롯당 **호출 한 번**이다. 아래 절 참고.

실증:

아래 표는 그 버린 방법으로 잰 값이다. 참고로만 남긴다.

| 요청 tm | 전체 해시 | 발표표시 해시 |
|---|---|---|
| 18:10 (T) | `956e5522` | `3491189d` |
| 18:00 | `61928db9` | `a4e46d00` |
| 17:50 | `23f74772` | `f3d254bc` |
| **19:10 (미래)** | `a44c3993` | **`3491189d`** ← T와 같다 |

미래 요청의 발표표시가 18:10과 같다 → **그 시점의 최신 발표분은 18:10**.
전체 해시가 다른 이유는 같은 발표분이라도 요청한 대상시각(ef)이 달라 그림이 다르기 때문이다.

## 측정값

| 발표 | 감지 | 지연 |
|---|---|---|
| 18:10 | 18:10:57 이전 | 1분 미만 |
| 19:30 | 19:31:05 | **+1분** |
| 19:40 | 19:41:48 | **+2분** |

`handoff-mac/docs/03-kma-api.md`는 "발표 +2~8분"이라고 적고 있으나,
**실측은 그보다 훨씬 빠르다.** 원본 문서의 값은 다른 API(격자)나 다른 조건의 것으로 보인다.

## ⚠️ 발표가 났다고 그림이 있는 것은 아니다

**이것이 가장 비싼 함정이었다.** 스탬프가 바뀌어 "새 발표"로 판정하고 받았더니
모든 `ef`가 빈 이미지였다.

```
19:38 시점 확인
  19:30 발표   1,431 bytes   색 1개   ← 빈 그림 (ef 10·20·30·60·120·240 전부)
  19:20 발표  71,617 bytes   색 많음  ← 정상
  19:10 발표  71,437 bytes   색 많음  ← 정상
```

발표 후 8분이 지나도 그림이 없었다. 스탬프는 다른 산출물 기준으로 먼저 바뀌는 듯하다.

그래서 **두 단계로 판정한다.**

1. 스탬프가 바뀌면 "새 발표 후보"
2. 실제로 받아 **크롭 결과의 색이 두 가지 이하면 빈 그림** — 저장하지 않고
   발표를 못 본 것으로 되돌린다(다음 주기에 다시 시도)

정상 그림은 해안선이 그려져 있어 색이 수십 가지다. 이 판정은 무강수여도 통한다.

### 보여줄 것이 하나도 없을 때

최신분에 매달리며 빈 화면을 오래 두느니, **뒤로 물러나며 그림이 있는 발표분을
찾아 받는다**(최대 6단계 = 1시간). 실제로 19:40이 비어 19:30을 대신 받았다.
화면 왼쪽 위에 `발표 19:30`이 붙어 어느 발표분을 보고 있는지 늘 알 수 있다.
운영하면서 `qpf_publish` 테이블에 지연이 계속 쌓이므로,
`GET /api/status`의 `publish`(n·min·p50·p90·max)를 보고 감시 구간을 좁히면 된다.

## ⚠️ 지금 시각의 발표분은 오지 않는다

**이것이 설계를 뒤집은 사실이다.** 처음에는 "발표 스탬프가 바뀌면 그 슬롯을 받는다"로
짰는데 틀렸다. 이 API는 지금 시각의 발표분을 바로 주지 않는다.

```
19:44 시점 · 현재 슬롯 19:40
  19:40 (지금- 4분)   1,438 b   빈 그림
  19:30 (지금-14분)  71,192 b   정상   ← 최신 가용
  19:20 (지금-24분)  71,763 b   정상
  19:10 (지금-34분)  71,673 b   정상
```

**최신 가용분은 보통 20~30분 뒤처진다.** 그래서 '정시 +n분에 확인' 같은 감시 창은
뜻이 없다. 그 창 안에서는 어차피 빈 그림만 온다.

## 지금 방식 — 가진 것 다음부터 앞으로 훑는다

```
가진 것 = 19:30
  → 19:40 확인 → 빈 그림 → 멈춤. 새 발표 없음 (호출 1회)

한참 뒤 19:40이 올라오면
  → 19:40 확인 → 정상 → 19:50 확인 → 빈 그림 → 멈춤
  → 가장 최신인 19:40 을 받는다 (호출 2회 + 장수)
```

- **정상 상태에서 사이클당 호출 1회.** 새 것이 없으면 한 번 찔러 보고 끝난다
- 새 것이 있으면 있는 만큼 앞으로 나아가고, **가장 최신 것만** 받는다
  (중간 것은 이미 지나간 예측이라 받을 이유가 없다)
- 처음 뜰 때는 가진 것이 없으므로 90분(`SCAN_BACK=9`)을 거슬러 훑는다.
  실측으로 확인 10회에 `19:30`을 찾아 9장을 받았다(지연 16.9분)

판정은 **그림이 실제로 있는지**로만 한다. 발표 스탬프는 그림보다 먼저 바뀌므로
믿을 수 없다 — 19:30 발표는 스탬프가 19:31에 바뀌었지만 그림은 19:38에도 없었다.

## 호출량

한 발표분의 장수 = **최대 선행시간 ÷ 간격**. 발표는 10분마다 나오므로
이 숫자가 곧 **10분당 호출 수**다. 화면 메뉴(예측 분포 재생 창)에서 바꾼다.

| 간격 | 선행 | 장수 | 10분당 | 시간당 | 하루 |
|---|---|---|---|---|---|
| 10분 | 6시간 | 36 | 36 | 216 | 5,184 |
| 10분 | 3시간 | 18 | 18 | 108 | 2,592 |
| **20분** | **3시간** | **9** | **9** | **54** | **1,296** |
| 30분 | 3시간 | 6 | 6 | 36 | 864 |

여기에 발표 확인 호출이 발표당 1~8회 더 붙는다.

받는 시간도 같이 줄어든다 — 36장 순차 수집에 약 35초 걸렸다.

⚠️ **한꺼번에 던지면 안 된다.** 36장을 동시에 요청하니 `ef=190~240` 6장이
통째로 실패했다. 순차 + 실패 1회 재시도로 36/36 성공한다.

## 저장 용량

`size=1800` 원본은 장당 약 130KB지만, **경남만 크롭하면 장당 약 19KB**다.
36장 한 발표분이 0.66MB. 기본값은 최근 3개 발표분만 남긴다(`keep`).


## 곁들여 잡은 자료 버그

매분 보강값이 **마지막 정시 칸을 덮어쓰고 있었다.** 12시간을 요청하면
`14 15 16 17 18 19:47` 처럼 나와, `19`시 정시 한 칸(18:00~19:00)이 통째로 사라졌다.
툴팁에 "최근 107분"이라는 이상한 값이 뜬 것이 단서였다.

이제 칸을 하나 더 붙인다 — `… 18 19 19:50`. '정시까지'와 '정시 이후 지금까지'가
둘 다 남고, 부분 구간은 마지막 정시의 `RN_DAY` 증분으로 계산해 겹치지 않는다.
