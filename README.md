# 경남 기상 대시보드

경상남도 18개 시군의 강수·특보·초단기예측을 한 화면에 표출하는 재난상황실 대시보드.
맥미니 상주 서버 하나로 수집·저장·표출을 모두 한다.

## 실행

폴더째 옮겨 놓고 실행 파일 하나만 누르면 된다. 가상환경 생성·의존성 설치·키 배치·
포트 찾기·브라우저 열기를 알아서 한다.

| | |
|---|---|
| **맥** | `run.command` 더블클릭 (또는 터미널에서 `./run.command`) |
| **윈도** | `run.bat` 더블클릭 |

처음 실행은 의존성을 받느라 1~2분, 뜬 뒤에도 자료를 받느라 화면이 채워지기까지
10~40초 걸린다. 받아 둔 것은 `data/` 에 남으므로 두 번째부터는 바로 뜬다.

포트를 바꾸려면 `PORT=9000 ./run.command`, 다른 기기에서도 보려면 `HOST=0.0.0.0`.
포트가 이미 쓰이고 있으면 다음 빈 포트를 알아서 찾는다 — **수집기가 둘 돌면
기상청 호출이 두 배가 되므로** 같은 포트에 겹쳐 띄우지 않는다.

### 직접 띄우기

```bash
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
mkdir -p config && cp handoff-mac/config/api_keys.txt config/   # 키는 저장소에 없다
.venv/bin/python -m app.main
```

윈도는 `.venv\Scripts\python.exe -m app.main`.

## 구조 — 수집과 표출을 분리한다

**화면을 열 때 기상청을 부르지 않는다.** 수집기가 주기적으로 받아 SQLite에 넣고,
웹은 저장된 것을 읽기만 한다. 접속자가 몇이든 기상청 호출은 한 번이고,
API가 죽어도 마지막 정상 자료가 화면에 남는다.

```
기상청 API ──▶ app/collectors/ ──▶ SQLite(data/gnweather.db) ──▶ /api/* ──▶ 화면
               (APScheduler)          + data/cache/qpf/*.png
```

| 파일 | 하는 일 |
|---|---|
| `app/config.py` | 키 로드, 수집 주기, 화면 폴링 기본값 |
| `app/kma.py` | 기상청 호출 한 곳. euc-kr, 타임아웃, 재시도, 200인데 본문이 오류인 경우 |
| `app/db.py` | 스키마. `quality` 열이 무강수·결측·조회실패를 가른다 |
| `app/domain/regions.py` | 관제순, 대표지점, 특보구역 세분화, 강원 고성 배제, 중대경보 파싱 |
| `app/collectors/rain.py` | AWS 정시(`awsh`) + 매분 보강(`nph-aws2_min`) |
| `app/collectors/forecast.py` | 초단기예측 격자 RN1(`nph-dfs_vsrt_grd`) |
| `app/collectors/alerts.py` | 기상특보(`wrn_now_data`) |
| `app/collectors/qpf.py` | 예측 분포 이미지(`nph-qpf_ana_img`) — 전국을 받아 PIL로 경남만 크롭 |
| `app/bangjae.py` | 스방(경남 스마트 통합 방재시스템) 호출 — 로그인, 조회 시각 규칙 |
| `app/collectors/bangjae_rain.py` | 스방 시군 평균·다우지점 + 지점별 시간강우량 |
| `app/maint.py` | 저장공간 재기·정리(보관 기간) |
| `app/demo.py` | 데모 사례 — 실제 호우 때를 되돌려 띄운다 |
| `app/queries.py` | DB 읽기. 결측을 0으로 더하지 않고 뺀 시간 수를 함께 준다 |
| `app/main.py` | FastAPI + 스케줄러 + `/api/*` |
| `app/web/static/index.html` | 화면 |

## 수집 주기

| 자료 | 주기 | 근거 |
|---|---|---|
| 특보 | 1분 | 발표 리듬이 없다. 아무 때나 나온다 |
| 강수량 | 10분 | 정시 자료 + 최근 구간은 매분자료로 보강 |
| 초단기예측 | 10분 | 발표 주기 10분, 실제 업로드는 발표 +2~8분 뒤 |
| 예측 분포 이미지 | 10분 | 발표분이 바뀔 때만 실제로 받는다 |
| 스방 강수량 | 10분 | 기상청과 같은 리듬. 다른 서버라 따로 돈다 |

화면의 갱신 주기는 **이것과 별개**다. 메뉴바에서 활성 창의 자료별로 따로 정하고,
바꿔도 기상청 호출량은 변하지 않는다 — 화면은 DB만 읽는다.

## API

| 경로 | 내용 |
|---|---|
| `GET /api/rain?hours=N&src=kma\|bangjae` | 지점별 시간대별 강수량 + 누적 (`bad`=결측 시간 수) |
| `GET /api/forecast?hours=N` | 읍면동·시군 예측 순위 |
| `GET /api/alerts` | 특보 현황(집계는 시군 수) |
| `GET /api/minute?n=N` | 지금 오는 비 — 15분·60분 강수량 상위 N곳 |
| `GET /api/qpf` · `/api/qpf/{tmfc}/{ef}.png` | 예측 분포 프레임 목록·이미지 |
| `GET /api/bangjae` | 스방 시군 **평균** 강수량 + 시군별 다우지점 |
| `GET /api/storage` · `POST /api/storage/cleanup` | 저장공간 현황 · 묵은 자료 지우기 |
| `PUT /api/settings/retention` | 보관 기간 |
| `GET /api/demo` · `/api/demo/{slug}` | 데모 사례 목록 · 꾸러미 |
| `GET /api/status` | 수집기 상태 + 발표 지연 통계 |
| `GET /api/settings` · `PUT /api/settings/qpf` | 예측 이미지 간격·선행시간 |
| `POST /api/refresh/{kind}?force=true` | 수동 조회 — 주기와 무관하게 실제로 다녀온다 |

## 과거를 얼마나 채워 두는가

수집기는 **화면이 고른 구간만큼만** 과거를 받는다(`rain_depth` 설정, 기본 26시간).
`/api/rain?hours=N` 이 들어오면 그만큼 깊이를 올리고 그 자리에서 한 번 받아 온다.
화면은 `missing`(아직 한 줄도 안 받은 시각 수)이 0이 될 때까지 몇 번 더 물어본다.

⚠️ 이게 없을 때는 **'2일'을 골라도 26시간 앞이 영원히 비어 있었다.** 그래프 왼쪽이
   통째로 빈 채였고, 다음 주기가 와도 채워지지 않았다 — 수집기가 26시간만 보기 때문이다.

⚠️ 오래된 시각이 빈 응답으로 오면 **결측으로 적어 둔다.** 그냥 넘기면 행이 하나도
   안 남아 매 주기마다 영영 다시 묻는다(기상청에 그 자료가 없는 것뿐인데).

## 저장공간

`설정 → 저장공간`에서 지금 얼마나 쌓였는지 보고 보관 기간을 정한다.
DB 한 파일과 예측 분포 이미지 캐시 두 군데에 쌓이는데 **이미지가 훨씬 빨리 자란다**
(한 발표분이 수십 장, 10분마다 새 발표분). 매일 새벽 4시 20분에 한 번 정리하고,
`지금 정리`로 즉시 돌릴 수도 있다. 되돌릴 수 없으므로 **오늘 것은 어떤 설정에서도 남긴다.**

## 판 대비 — 모니터마다 다르다

⚠️ **같은 색이 화면마다 다르게 보인다.** 맥에서는 바탕 `#090D13` 과 판 `#111823` 이
또렷이 갈라지는데, 흔한 윈도 모니터에서는 둘 다 '까만색'으로 뭉개져 판의 경계가
사라진다. 감마와 색역이 달라서다. 코드에 한 값을 박아 두면 어느 한쪽에서는 반드시
틀리므로, 보는 사람이 자기 화면에서 맞추도록 열어 뒀다.

`설정 → 화면 꾸미기`

| 조절기 | 하는 일 |
|---|---|
| **판 대비** | 바탕을 어둡게 밀고 판을 조금 들어 올린다. 테두리도 함께 세운다 |
| 바탕색 · 판 색 | 직접 지정. `✕` 를 누르면 자동으로 돌아간다 |

판을 크게 밝히지 않는 까닭은 글자가 그 위에 얹히기 때문이다 — 본문 대비가 같이
흔들린다. 끝까지 올려도 `#E8EEF6` 글자의 명암비는 15.5:1 → 13:1 로, 기준(7:1)보다
한참 위다. 밝은 테마는 판이 이미 흰색이라 더 들 곳이 없어 바탕만 민다.

⚠️ 대비 0은 **손대지 않은 것과 완전히 같아야 한다.** 판 계열을 판 색에서 늘
   계산하면 그게 깨진다 — 기본 토큰들이 판 색을 그냥 밝힌 값이 아니라 색조가
   조금씩 다르기 때문이다(계산하면 `#1E2836` 이 `#222832` 로 나왔다). 그래서 판 색을
   직접 고르지 않았으면 기본 토큰을 같은 만큼만 들어 올린다.

## 종합 화면 구성

왼쪽에 강수 타임라인, 오른쪽 위에 예측 분포 재생, **오른쪽 아래**에 한 판이 더 들어간다.
그 자리에 무엇을 놓을지 `설정 → 종합 화면`에서 고른다.

| | 무엇 |
|---|---|
| 예측 상위 시군 | 초단기예측 격자에서 뽑은 읍면동 순위 |
| 지금 오는 비 | **15분·60분 강수량 상위** — 왼쪽 칸 15분, 오른쪽 칸 60분 |

`지금 오는 비`는 **기상청 매분자료(`nph-aws2_min`)만 쓴다.** 스방에는 분 단위가 없다.
15분치를 왼쪽에 두는 까닭은 그게 제일 빠르기 때문이다 — 60분치는 이미 지나간 한 시간을
담고 있어서, 막 쏟아지기 시작한 곳을 한 박자 늦게 알린다. 한 칸에 몇 곳을 세울지는
설정에서 정한다(4~16곳).

15분 칸 머리의 토글로 **`그대로 ↔ ×4`** 를 오간다. 둘은 같은 값의 다른 표기다 —
15분에 12.5㎜는 `×4` 로 보면 50㎜/h 이고, 이건 '시간당 50㎜의 기세'라는 뜻이지
한 시간에 50㎜가 온다는 말이 아니다(그 기세가 이어질 때의 값이다). 환산해서 봐야
60분치·특보 기준(시간당 ㎜)과 같은 자로 견줄 수 있고, 그대로 봐야 실제로 떨어진 양을
안다. 자료를 다시 받지 않고 표기만 바꾼다. `×4` 일 때는 색 단계도 60분 것을 쓴다.

⚠️ 두 값은 **각자 제 시각**을 찾는다. 낡은 수집기가 15분치를 안 넣고 덮어쓰면 그 시각의
   15분 칸이 통째로 비는데, 그때 화면을 비워 버리면 멀쩡한 직전 자료까지 사라진다.
   시각이 서로 다를 때만 각 칸 머리에 그 시각을 적는다.
⚠️ 막대 색은 두 칸이 **다른 단계표**를 쓴다. 같은 눈금으로 칠하면 15분에 8㎜
   (시간당 32㎜의 기세)가 옅은 색으로 묻힌다.

## 합계 칸

**숫자만 적는다.** 예전에는 값에 따라 칸을 색으로 채우고 특보 기준을 넘으면 테두리까지
둘렀는데, 바로 옆 막대가 이미 같은 말을 하고 있어 한 화면에서 같은 사실을 세 번 강조하는
꼴이었다. 결측 시간 수(`1h`)도 여기 적지 않는다 — 값인지 단위인지 읽히지 않았다.
알아야 할 때는 줄에 마우스를 올리면 나온다.

## 누적 막대 눈금

**늘 실제 값에 맞춘다.** 예전에는 특보 기준(110/180㎜)까지 눈금을 늘려 놨는데,
6.8㎜가 온 날은 막대가 3%밖에 안 차 아무것도 못 읽고 600㎜가 오면 넘쳤다.

**점선 두 줄도 실제 값에서 뽑는다.** 그때 화면에 있는 시군 누적값의 **중앙값**과
**상위 25%**(75분위)다. 값이 바뀌면 두 줄도 함께 움직인다.

⚠️ 예전에는 여기에 호우특보 12시간 기준(110/180㎜)이 박혀 있었다. **강수량은
   그보다 훨씬 유동적이다.** 900㎜ 온 날에는 두 줄이 막대 왼쪽 끝(12%·20%)에
   나란히 붙어 어느 시군도 가르지 못했고, 5㎜ 온 날에는 눈금 밖이라 아예 긋지도
   못했다. 어느 쪽이든 '기준'이 하는 일이 없었다. 분위수는 5㎜ 오는 날에도
   900㎜ 오는 날에도 늘 눈금 안에 있고, 늘 같은 것을 말한다 — **이 시군이 도
   전체에서 어디쯤인가.**
⚠️ 특보 예약색(주의보 노랑·경보 빨강)으로 긋지 않는다. 특보 기준이 아니기 때문이다.
   무강수라 중앙값이 0이면 그 줄은 긋지 않는다.

한 시군만 유독 길면 나머지가 다 뭉개진다. 그때는 눈금을 한 번 꺾어(broken axis)
뒷부분을 눌러 담고, 꺾은 자리에 **물결 자국**을 남긴다. 실측: 662㎜ 한 줄과
150㎜대 여럿이 섞였을 때 — 꺾기 전 142.5㎜는 21.5%였고, 꺾은 뒤 58.1%가 되어
서로 견줄 수 있게 됐다.

## 묶음 칸은 다른 자로 잰다

히트맵은 지난 시간을 `01~23` 처럼 묶어 한 칸에 담는다. **그 칸은 1시간 칸과
색조도 눈금도 다르다** — 시우량 램프는 청색(`--rain-*`), 묶음 램프는 청록(`--acc-*`).

⚠️ 같은 램프로 칠했을 때 **23시간 합계 64.5㎜가 1시간 50㎜와 똑같은 최고 단계**로
   앉았다. 오래 묶을수록 무조건 진해지는 바이어스다 — 색이 '많이 왔다'가 아니라
   '오래 묶었다'를 말하게 된다.

눈금은 **묶음 길이마다 따로, 그때 화면에 있는 실제 값에서** 잡는다(`ACC_FRAC`).
길이가 다른 두 묶음은 각자 제 눈금을 쓴다 — 한 눈금에 얹으면 긴 쪽이 늘 이긴다.
칸은 세로로 읽는 것이다(이 구간에서 어느 시군이 두드러지나). 실측(8.28. 사례):

```
23시간 묶음  최대 64.5㎜  →  64.5 가 그 열의 최고 단계
24시간 묶음  최대 105㎜   →  같은 64.5 는 중간 단계
```

0.5㎜를 최고 단계로 칠하지는 않으려고 눈금 바닥을 10㎜로 둔다.

## 데모 시연

비가 안 오는 날에는 화면이 온통 0.0 이라 무엇을 보여 주는 화면인지 알 수 없다.
`표시 → 데모 시연…`(또는 `설정 → 데모 시연`)에서 실제로 호우가 내렸던 때를
그대로 되돌려 띄운다. 화면을 점검할 때 쓴다 — 비가 안 오는 날에는 무엇이 고장 나도
0.0 이라 알 수가 없다.
보는 동안 화면 맨 위에 띠가 떠 있어 실황과 헷갈리지 않는다.

|---|---|
| 2026.8.28. 경남 호우 | 실측. 김해 율하 123.5㎜/일, 창원 111.0㎜/일 |
| 2026.8.28. 11시 — 한창 올 때 | 봉우리에서 끊은 화면. **그때 발표된 초단기예측이 함께 담겼다** |
| 2026.8.28. 호우 ×2 | **가상.** 같은 실측을 두 배로 키운 시연용 — 경보까지 걸린 화면 |

**강수량도 초단기예측도 실측이다.** 스방 265개소의 시간강우량과, 격자 API
(`nph-dfs_vsrt_grd`)로 받은 **그 시각의 실제 발표분**을 파일로 굳혀 둔다
(8.28. 11시 발표 → 남해 고현면 20㎜, 창원 진동면 20㎜).

담지 못한 것이 둘 있다.

- **특보.** 이력 API(`wrn_met_data.php`)가 이 키로 403 이라 과거 발표 내역을 받을 수 없다.
  그래서 담긴 강수량에 호우 기준(3시간 60/90㎜, 12시간 110/180㎜)을 적용해 **산출**하고,
  화면에 `산출`이라고 적어 발표 내역과 구분한다.
- **예측 분포 이미지.** `nph-qpf_ana_img` 는 과거 시각이 404 다. 최신분만 나온다.

예측이 안 담긴 사례에서는 **예측을 비운다** — 오늘 예측을 8월 자료 옆에 붙이면
통째로 거짓말이 된다. 분 단위 자료도 마찬가지라 `지금 오는 비` 판은 데모에서 비워 둔다.

⚠️ 스방은 며칠치만 남긴다. 그래서 사례를 **파일로 굳혀** 두고, 새 사례는 원본을 다시
   받는 대신 굳혀 둔 파일에서 잘라 만든다(`build_cut`).

## 스방 자료

기상청과 **다른 관측망**이다. 경남 자체 AWS 212개소에 기상청 것을 더해 **시군 평균**을
낸다. 기상청 값은 시군 대표지점 하나이므로 두 숫자는 뜻이 다르고, 실제로 자주 어긋난다
(고성 학림 500.5mm를 기상청 AWS는 아예 못 본다). 그래서 `obs_hourly` 에 섞지 않고
`bangjae_rain` 에 따로 쌓고, 화면에도 출처를 밝혀 적는다.
같은 응답(`dt090/list3`)에서 시군별 **다우지점**(그 시군에서 제일 많이 온 곳)도 함께
받는다 — 따로 부르면 두 값의 기준시각이 어긋난다.

### 지표가 자료원을 정한다

표 머리글을 누르면 `대표지점 → 다우지점 → 시군 평균`으로 돌아가고, **관측망도 같이 바뀐다.**

| 지표 | 자료원 | 왜 |
|---|---|---|
| 대표지점 | 기상청 56개소 | '시군 대표지점'은 기상청 관측망의 개념이다 |
| 다우지점 | **스방 265개소** | 후보가 다섯 배. 56개소로 고르면 창녕 계성 28.5㎜를 아예 못 본다 |
| 시군 평균 | **스방 265개소** | 56개소로는 창원이 5개소·진주가 3개소다. 그걸 시군 평균이라 부를 수 없다 |

스방 265개소면 창원 23·진주 18·합천 23개소가 되고, 다우지점은 스방이 스스로 내는
`rtu_area` 와 비가 온 모든 시군에서 일치한다(계성·마상·가야산·상동·구기·오부·서하…).
머리글 옆 딱지가 지금 어느 관측망인지 늘 밝힌다. 스방이 멈추면 기상청으로 물러서고
딱지가 `스방 안 됨→기상청` 으로 바뀐다 — 조용히 다른 값을 보여 주지 않는다.
설정 → 자료에서 한쪽으로 고정할 수도 있다.

시군 평균 줄은 `창원²³` 뿐이다 — 시군명만 크게, 개소 수는 윗첨자. 줄을 찾는 눈은
시군을 보지 '평균 23개소'를 보지 않는다. 시군을 누르면 같은 기간의 **지점별 강수량**이
많이 온 순으로 펼쳐지고, 몇 개소가 자료를 주는지도 함께 적는다.

### ⚠️ 스방 기간조회(list3)와 값이 다른 두 가지 이유

화면은 **그린 시간 칸을 그대로 더한다** — 표의 누적은 곡선의 합이어야 하기 때문이다.
스방의 시군별 강우량 화면(`dt090/list3`)과 대조해 보니 어긋나는 자리가 둘 있었고,
둘 다 **시간강우량(dt096) 쪽이 맞았다.** 실측 근거를 남긴다.

**하나. 여러 날을 걸치면 첫날이 한 번 더 세어진다.** `일누적`이 다음날 01시에야
리셋되는 구조라 그렇다.

```
사천 곤양  9.3. 시간강우 합계 30.5㎜  →  9.3.~9.5. list3 다우지점 61.0㎜  (= 30.5 × 2)
창녕 계성  9.2. 에 28.5㎜            →  9.3. 하루만 조회해도 계성 28.5 가 얹혀 온다
```

**둘. 시군 집계에서 기상청 관리 지점이 빠진다.** 스방은 같은 시군을 관리주체에 따라
`창원`(경남)·`창원시`(기상청)로 나눠 담는데, list3 의 시군 줄은 경남 쪽만 센다.

```
창원 9.3.  경남 18개소 평균 2.56 (최대 오동 27.5)
           기상청 5개소 평균 14.58 (최대 마산회원 44.5)  ← 여기가 통째로 빠진다
           전부 23개소 평균 5.17 (최대 마산회원 44.5)
           list3: 평균 3.7 · 다우지점 '오동(27.5)'
```

즉 그날 창원에서 제일 많이 온 곳은 **마산회원 44.5㎜**(15시에 43.5㎜)인데 스방 화면은
오동 27.5㎜를 다우지점으로 내놓는다. 대시보드는 265개소를 다 보므로 마산회원을 잡는다.
처음에 기상청 AWS 56개소를 버린 이유(고성 학림 500.5㎜)와 같은 종류의 누락이다.

하루를 통째로, 한쪽 관리주체 쏠림이 없는 시군으로 대조하면 둘이 정확히 맞는다
(사천 7.62 vs 7.3, 진주 0.97 vs 1.0, 하동 4.14 vs 4.1, 고성 1.40 vs 1.4).

**조회 시각 규칙.** 스방은 `toTime=H` 를 '**H시까지**'로 본다. 지금이 06:47인데 06으로
물으면 06:00에서 잘려 **지금 오는 비가 빠진다.** 그래서 **다음 정시(07)로 조회**하고,
받은 값은 07시치가 아니라 지금까지의 값이므로 **기준시각은 `지금 - 5분`(06:42)으로
저장**한다. 없는 시각을 적지 않으려는 것이다. 23시대에는 다음 정시가 없어 23으로 둔다.
규칙은 `app/bangjae.py` 의 `as_of()` 한 곳에 있다.

**계정은 필요할 때만 쓴다 — 없다고 건너뛰지 않는다.** 부르는 자리에 따라 로그인 없이도
자료가 그대로 온다. 상황실 내부망 PC 에서 실측(2026-09-05): 계정 없이 `dt090/list3`
18개 시군, `dt096/list` 532줄이 왔다. 그래서 **일단 부르고, `[]` 가 올 때만** 로그인한다.

⚠️ 예전에는 계정이 없으면 한 발도 안 떼고 건너뛰었다. 그 바람에 상황실에서는 화면이
   늘 `스방 안 됨→기상청` 이었다 — **서버는 멀쩡했고 부르지를 않았다.**
   수집기록에 `스방 계정 없음 — 건너뜀` 만 남아 있어 조회 실패와 구분되지 않았다.

계정이 필요한 자리라면 `config/api_keys.txt` 의 `BANGJAE_ID`/`BANGJAE_PW` 로 넣는다.
비워 두면 옆 프로그램(`code/bangjae`)이 DPAPI로 저장해 둔 계정을 쓴다. 둘 다 없는데
서버가 로그인을 요구하면 이 수집기만 `조회 실패`로 남고 나머지는 정상 동작한다.

주소는 `BANGJAE_URL` 환경변수 또는 `config/api_keys.txt` 의 `BANGJAE_BASE` 로 바꾼다
(기본 `http://112.100.10.186:8080`). 내부망 밖에서는 이 주소가 응답하지 않으므로
**연결 타임아웃만 5초**로 따로 두었다 — 한 번이 60초씩 걸리면 10분 주기를 갉아먹는다.

**내부망 SSL.** 내부망 장비가 인증서를 갈아 끼워 기본 설정으로는 검증에 걸린다.
`DISABLE_SSL_VERIFICATION` 이 기본 켜짐(=검증 안 함)이고, 끄려면 `0` 으로 둔다.

## 예측 이미지 호출량

한 발표분의 장수 = **최대 선행시간 ÷ 간격**. 발표가 10분마다 나오므로
이 숫자가 곧 10분당 호출 수다. 화면의 `예측 분포 재생` 창 메뉴에서 바꾼다.

| 간격 · 선행 | 장수 | 하루 호출 |
|---|---|---|
| 10분 · 6시간 | 36 | 5,184 |
| 20분 · 3시간 | 9 | 1,296 |
| 30분 · 3시간 | 6 | 864 |

**발표가 났는지 먼저 확인하고 난 것만 받는다.** 미래 시각을 요청하면 최신
발표분이 오는 성질을 이용해, 이미지에 찍힌 발표시각 표시를 해시로 비교한다.
확인은 호출 한 번이고, 정시 이후 감시 구간에서만 한다.
재는 방법과 실측값은 `docs/02-발표주기.md`.

## 지켜야 할 것

- **비밀은 저장소에 넣지 않는다.** `config/api_keys.txt`·`.env`는 `.gitignore`에 있다.
  로그에도 남지 않게 httpx 로거를 WARNING으로 낮춰 뒀다(요청 URL에 `authKey`가 실린다).
- **조회 실패와 '자료 없음'을 구분한다.** 실패는 저장하지 않고 다음 주기에 다시 시도한다.
  DB의 `quality`, 화면의 `0.0` / `—` / `✕`가 그 구분이다.
- **시각은 전부 KST.** UTC로 바꾸지 않는다(기상청 API가 KST를 쓴다).

함정 목록은 `handoff-mac/docs/05-pitfalls.md`, 화면 설계는 `handoff-mac/docs/07-dashboard-design.md`.
